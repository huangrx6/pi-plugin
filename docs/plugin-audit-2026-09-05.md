# Pi 扩展逐包审查

本次审查按代码、日常使用和终端 UI 三个维度检查 8 个扩展，并用每个包自己的 `npm run check` 与 `npm test` 验证。当前全量结果为：8 个包的类型/语法检查通过；自动压缩 28 项、Footer 14 项、权限模式 10 项、通知 54 项、额度 39 项、技能 7 项、任务清单 893 项、策略引擎 246 项全部通过。

## 已落地的共性治理

| 项目 | 结果 |
| --- | --- |
| 配置归属 | 自动压缩、权限模式、任务清单只使用各自的 `extensions-data/<package>/` 规范目录；旧目录不再在运行时被扫描。 |
| 状态污染 | 技能被重复 `read` 时不再重复写入“技能已加载”记录。 |
| 面板入口 | 每个需要参数或诊断的扩展保留无参数面板，日常路径先显示当前状态，再进入动作或诊断。 |
| 失败策略 | 网络额度、策略识别、压缩续跑、通知终端转发都保留明确失败状态，不把未知当成功。 |
| 包发布 | 修改过的包版本与最新 CHANGELOG 条目同步；根 manifest 仍包含全部 8 个扩展。 |

## pi-policy-engine

代码上已经切到模型优先意图识别：实时识别失败会阻止策略执行，不再用本地规则静默兜底；中断任务仍会重新识别，并在识别结果的策略指纹未变化时复用现有注入，避免重复注入。Host agent recognition 使用当前 Pi 模型，endpoint 仅作为显式配置的跨平台适配。

使用上，`/policy` 是一级日常面板，复杂配置放在规范配置文件中；面板操作不会要求用户理解一次性模式、运行时 profile 等内部概念。

UI 上，识别期间使用 Pi 的 Working 状态显示“意图识别中…”，识别完成后恢复工作状态；策略活动记录折叠显示事实，展开显示来源、原因和实际注入。当前剩余优化点是把识别耗时、失败原因和复用次数加入诊断统计，便于评估不同模型的识别质量。

## pi-auto-compact

代码上已删除旧 `pi-context-qos` 配置读取和阈值换算逻辑，避免新旧预算口径混用。运行时只读取全局规范配置和受信任项目覆盖，配置解析失败会停用并提示原因。

使用上，`/context` 无参数先给三项面板：用量、暂停/恢复、阈值；阈值只在当前会话生效，持久化仍通过配置文件完成。

UI 上，状态条区分未知用量、压缩中、压缩失败和暂停；压缩活动记录可展开查看 token 变化。剩余优化点是把“当前会话覆盖”与“配置文件值”在面板中并列显示，减少用户误以为命令已永久保存的可能。

## pi-mode-switcher

代码上已删除旧 `mode-switcher.json` 回退读取，权限模式的来源唯一。Bash 复合命令会逐段检查，无法证明只读的复合命令按写入处理；高风险管道会触发确认。

使用上，`/mode` 无参数打开三项选择，参数命令只保留熟悉模式的快捷入口。模式保存跨会话，但写入失败不会阻断当前操作。

UI 上，确认框显示清理并按终端宽度裁切后的命令、路径或 URL，状态条只显示当前模式。剩余优化点是把“ask / smart / full”在选择器中改成更短的中文主标题，把英文 key 放到说明尾部，降低首次使用的理解成本。

## pi-quota-status

代码上适配器按服务、地区和端点严格匹配；请求有 15 秒超时、AbortController、凭证摘要隔离和晚到响应失效保护。订阅用量、账户余额、Key 限额不互相推断。

使用上，`/quota` 先查当前服务；刷新、账户余额和数据来源诊断进入面板二级动作。RPC/JSON/print 模式不打开选择器。

UI 上，未知值显示 `--`，暂时性失败保留短时间成功值并明确标记过期，额度摘要进入状态条。剩余优化点是为“当前服务未适配”和“未配置凭证”提供面板内可复制的环境变量名提示。

## pi-skill-inject

代码上技能发现、内容读取和路径规范化按会话缓存；token 匹配要求明确边界，URL 和中文后缀不会误注入。此次补上了重复 `tool_result` 去重，重复读取同一技能不会制造重复活动记录。

使用上，用户只需在正文输入 `/<skill-name>`，补全负责发现候选；`/loaded-skills` 只用于查看当前分支记录。

UI 上，加载记录折叠显示技能名，展开显示完整来源路径；文本先清理终端控制序列并按实际显示宽度裁切。剩余优化点是为“技能文件读取失败”提供一次重新加载候选的动作，避免用户只能手动 `/reload`。

## pi-footer-composer

代码上 Footer 不依赖其他扩展的模块，只消费 Pi 聚合状态；状态按 `usage:`、`integration:`、`config:` 前缀路由，未知项进入配置行，文本经过终端控制序列清理并按字素宽度布局。

使用上，`/footer` 提供紧凑、完整、Pi 原生三项选择；选择仅作用于当前扩展进程，避免产生额外配置文件。

UI 上，窄终端会贪心换行，中文、emoji 和组合字符不会被截断；原生视图可立即恢复。剩余优化点是把当前模式在选择器标题中同时显示“信息密度”和行数，帮助用户快速选择。

## pi-todo

代码上生产路径已经以工作区 ScopeKey 和 durable store 为唯一状态来源；本次删除 agent 根目录 `pi-todo/` 回退，避免新旧目录形成 split-brain。提交使用 revision/CAS，依赖和状态迁移由纯 reducer 校验。

使用上，`/todos` 先进入当前工作集面板，再按任务状态提供动作；历史、依赖图查询和批量归档都是次级入口。模型通过 `todo` 工具维护清单，用户面板不需要记住全部命令。

UI 上，编辑器上方只显示当前任务和有限进度；完整列表按运行中、可开始、被阻塞分组并限制行数，超出部分给出继续查看入口。剩余优化点是把持久化冲突的“请重试”进一步变成面板中的刷新动作，降低并发会话下的恢复成本。

## pi-notify

代码上通知只在 TUI 且真实 TTY 中写终端控制序列；协议、复用器路径和未知终端都显式诊断，不执行系统命令。通知等待重试和排队续接结束后再发送，最终结果以模型 stop reason 为准。

使用上，`/notify` 是每日摘要和测试入口，`status` 才展开诊断；会话开关不写盘，环境变量负责长期关闭。

UI 上，主面板只显示开关、终端就绪和最近结果，协议细节放到二级页；发送结果明确表示“已写入终端”，不虚报系统已展示。剩余优化点是为“终端不可用”增加一键生成 `bell` 配置提示。

## 进入测试阶段的判断

当前可以进入扩展级测试和 Pi 实机验收。代码与离线回归已经通过，接下来需要在真实 Pi 运行时验证三类宿主差异：消息进入后的 Working 状态、多个扩展同时注册状态条时的显示顺序，以及切换会话/分支/模型后的 UI 清理。若这些验收通过，下一步才是把本地修改安装到实际 Pi 环境并执行 `/reload`。
