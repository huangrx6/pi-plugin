> 后续实施：本清单保留早期审查证据；当前行为以 [设计说明](DESIGN.md) 和 [更新记录](CHANGELOG.md) 为准。在线任务关系和意图由模型识别，失败会阻断本轮；确定性规则仅服务于离线预览、审批解析和结构安全检查。回合结果仍只标记“未验证”，尚未实现通用验证证据协议或历史学习。

审查日期：2026-09-05。审查版本：0.25.2。范围：策略插件的任务识别、阶段与授权、配置、模型适配、注入、持久化及测试。

结论：应立即补充真实场景回归测试，并先修复授权误判、旧任务污染和阶段指令冲突，再进入扩大范围的实际使用验收。现有测试通过不能作为这些行为已经正确的依据。

## 1. 必须优先修复的行为

### 1.1 授权识别忽略否定、引用及问句上下文

优先级：P0。已复现。

| 输入（存在待确认计划） | 当前结果 | 应有结果 |
| --- | --- | --- |
| 不要自主执行，等我确认 | approve | 保持待确认 |
| 解释一下“自主执行”是什么意思 | approve | 回答问题，保持待确认 |
| 好的，保持 API 兼容 | revise | 识别批准及附带约束，再判断约束是否改变已批准范围 |

`src/core/approval.js:293` 在其他语义检查之前直接匹配 `AUTONOMY_GRANT_RE`；含有“自主执行”就可能释放等待。简单增加几个肯定短语会同时扩大误释放范围。

建议：把授权解析成独立结构，区分肯定、否定、引用、提问、作用对象、范围和撤销。授权必须绑定当前任务及计划版本。保留有范围的自主授权，并根据新增约束是否扩大范围决定是否需要再次确认；不要将所有约束都机械视为新一轮审批。

### 1.2 明确只读请求可能被识别为修改

优先级：P0。已复现。

| 输入 | 当前结果 |
| --- | --- |
| 审查当前项目，只分析，不修改 | review / quick / mutate |
| 请检查 RabbitMQ 模型路由和向量库写入使用链路 | coding / standard / mutate |

`src/core/intent.js:129` 的否定词没有覆盖“不修改”的“不”；同一子句中的修改动词又优先于只读动词（约第 388 行）。“检查……写入链路”的业务名词也会贡献“写”的修改信号。

建议：以用户请求的动作和对象作为主干，区分“检查写入链路”和“实现写入链路”，统一处理否定作用域。只读请求、被讨论的动作、实际授权执行必须分开。验收应包含否定位置、标点、引用、名词化动作和中英文变体。

### 1.3 待确认状态抢先处理所有后续消息，缺少新任务判断

优先级：P1，真实案例直接命中，当前代码可复现。

`extensions/policy-engine/lifecycle.js:195` 先检查 `awaiting_approval`，随后所有输入都交给计划回复分类器，尚未判断它是不是新的任务。

- 用户的全面审查请求被归为 `revise`。
- 普通修订合并保留旧 `taskType / executionIntent / flow / profile`，风险只升不降，领域与关注项持续累积。
- 因此本次审查继承了旧的排障、修改、生产和数据库等上下文。
- 即便补充更多“审查”关键词，该分支仍然可能绕过新任务路由。

建议：在计划回复分类之前，先识别消息与当前任务的关系：继续、讨论、修订、批准、取消、切换任务、普通对话。新任务重新建立意图和风险；旧计划可保留为暂停状态，不能强迫新任务继承其授权和领域。风险单调上升只能应用于同一任务范围内。

### 1.4 等待批准时加载了已经批准的执行策略

优先级：P0。已复现为注入指令冲突；未声称模型实际发生了越权操作。

`src/core/loader.js:272` 仅判断 `phase === planning`，其余严格阶段均选择 `rigor.strict-execute`。

当用户问“为什么第二步要这样做？”时，阶段仍为 `awaiting_approval`，正文却包含 “The plan has been approved.”，尾部再要求不要执行。模型同时收到相反要求。

建议：采用显式阶段到策略的映射；`planning` 和 `awaiting_approval` 都不能包含已批准执行的表述。对整个最终注入块做一致性断言，而不只是测试末尾包含“不要执行”。

### 1.5 普通对话没有独立处理路径

优先级：P1。已复现并在磁盘历史中确认。

- 新状态下“你好”被识别为 `coding / medium / standard / unclear`，没有任何分类理由。
- 待确认状态下“你好”被识别为 `revise`；批准短语中的单字“好”与剩余文字“你”参与了这个误判。
- `activity.js` 把 `coding` 直接翻译成“代码修改”，掩盖了实际意图仍为 `unclear` 的事实。

建议：提供普通对话的轻量处理路径，不选择工程流程，也不推进或覆盖任务状态。摘要应分别显示任务类型与执行意图，例如“项目审查 · 只读”，避免把兜底分类显示成用户已经授权修改。

## 2. 阶段与状态需要完善的部分

### 2.1 回合结束与任务完成混在一起

优先级：P1。代码确认，见 `lifecycle.js:384`。

`agent_end` 无条件把 `planning` 推进到等待批准，把 `executing` 置为 `idle`；处理器不检查实际计划产物或完成证据。已有实现没有独立的验证完成状态。

建议：分开保存“本轮结束”和“任务结果”。最小结果集合可包含进行中、等待用户、受阻、失败、待验证、已验证完成。阶段推进需要关联计划或验证证据；缺乏证据时标为未验证，不能宣称任务已完成。先完善行为记录，不扩展为通用调度运行时。

### 2.2 跨会话恢复只绑定目录，没有绑定具体计划

优先级：P1。代码与保存字段确认，见 `src/core/history-store.js:168`、`:196`。

严格状态保存了目录、时间、阶段、部分 decision 字段；没有 sessionId、taskId、planId、计划正文引用或批准范围。相同目录的两个会话共用同一个文件；新会话也可能恢复另一个任务的待确认状态。

建议：绑定会话、任务、计划版本及分支上下文，恢复时校验引用是否存在。跨会话继续任务要能识别具体对象。同一目录不能自动等同于同一个计划。持久化写入采用原子替换并明确并发行为；关键状态写入应可等待并报告失败。

### 2.3 切换模式与关闭语义需要统一

优先级：P1。代码确认。

- 旧的一次性模式、运行时 profile 和独立 save 命令已移除；日常修改统一从一级面板立即写入全局配置。
- 关闭、取消、重置都通过同一持久化入口清理当前任务和对应的会话状态，避免产生幽灵审批。

建议：定义每个命令对当前任务、下一轮、文件配置及持久化状态的作用。命令与菜单共用一个状态变更入口。关闭、取消、暂停、重置应具有明确且一致的语义；涉及用户已有授权时按任务范围保留或撤销。

## 3. 保存的信息：现状与改进

本次读取快照：

| 数据 | 实际发现 | 能说明什么 |
| --- | --- | --- |
| history.jsonl | 374 条，字段仅 ts/source/prompt/task/risk/workflow/profile/confidence | 可看分类摘要，不能复原完整决策 |
| strict-state 文件 | 38 个：32 个指向 smoke 临时目录、4 个空文件、2 个真实项目 | 测试数据进入了真实用户目录 |
| 两个真实项目状态 | 理由分别为 209 条与 388 条，其中 plan-revision 分别为 66 条与 88 条 | 修订理由不断累积，不能当成干净的当前任务说明 |
| 会话策略卡 | 保存了当时的 decision、phase 和完整 injected 文本 | 能核对当时提供给模型的要求；不能证明模型遵守 |

### 3.1 先隔离测试产生的数据

优先级：P1。文件证据与 `scripts/smoke-extension.mjs:11` 共同确认。

冒烟测试只隔离了 cwd，没有隔离 agent 数据目录。真实 history 中，“只改 README 中的一处描述”有 50 条，“设计生产环境 PostgreSQL 数据库迁移方案并实施，不能停机，需要回滚”有 51 条，与测试固定输入吻合。不能把这些记录用于估计真实用户误判率。

建议：测试入口统一创建临时 agent 数据目录，等待异步写入完成后清理。先确认隔离生效，再备份并清理能够确定来源的旧测试数据；不能仅凭某条提示词像测试就删除。审查本身没有清理这些文件。

### 3.2 完整记录状态变化，避免历史断层

优先级：P1。

`state.js:59` 仅保存最多 80 字符的输入摘要；没有项目、会话、任务标识、意图、阶段变化、审批判定、模型、配置来源、注入版本及实际结果。`lifecycle.js:336` 的记录入口位于新任务分支，计划讨论、修订、批准等提前返回，不进入同样的历史记录。

建议每次决策至少记录：schemaVersion、extensionVersion、sessionId、taskId、planVersion、输入消息引用、关系判定、intent、phaseFrom/To、授权结果、配置指纹、策略指纹、当前 provider/model。完整输入及注入文本优先引用宿主会话记录，避免再建一份无上限的全文存储。

### 3.3 当前状态与审计事件分开保存

优先级：P1。

`state.js:290` 不断追加全部旧理由。当前状态应只保留有效约束、未解决问题和当前分类依据；历史变化放入有界事件记录，记录新增、撤销、替换及来源。对理由去重并设置上限，不能让历史假设一直作为当前依据出现。

这些数据目前没有进入向量库，也没有形成基于历史纠正的学习机制。history 主要供查看，严格状态用于恢复等待，活动卡用于解释注入。建议先补齐可回放和用户纠错，再考虑检索；授权及阶段判断应保留确定性来源，不能依赖相似度检索结果自动恢复。

## 4. 配置与模型适配体验

### 4.1 配置校验尚未覆盖完整结构

优先级：P1。已复现，见 `state.js:303` 和 `src/core/config.js:197`。

| 配置 | validate 当前行为 |
| --- | --- |
| domainHints 为字符串 backend | 通过 |
| showStatus 为字符串 false | 通过 |
| recognition.enabled 为字符串 true | 通过 |
| projectPolicyMaxBytes 为 -1 | 通过 |
| includePolicies 为数字 123 | 抛出异常，未返回校验报告 |

建议：共享一份完整 schema，覆盖对象、数组元素、布尔值、枚举、整数边界和跨字段约束；加载、命令校验和编辑共用它。展示每个有效值的来源、被覆盖值和规范化结果。动态读取配置时先完整校验，再整体采用，失败保留上次有效配置并给出诊断。

### 4.2 preview 与实际运行不一致，而且会调用语义服务

优先级：P1。已用 fetch 替身复现一次调用。

`state.js:519` 创建全新状态，忽略运行时模式、一次性覆盖、待确认计划和连续任务上下文；又调用允许语义回退的 `decide`。README 声称 preview/diff 不调用语义回退，与实现不符。

建议：默认预览使用当前上下文的副本，并明确显示作用范围；另提供从新任务开始的预览方式。默认禁用网络，语义预览明确选择后才使用。两条路径共用决策管线，预览不写入执行状态。显示确定性结果、语义结果和最终结果的差异。

### 4.3 模型适配具备基础，但扩展不够方便

优先级：P2。

已有能力：从宿主读取当前 provider/model；模型切换后重新选择适配策略；从待确认状态执行时也会重新计算模型适配。本次复现中旧状态配合 DeepSeek 模型正确选择了 `model.deepseek`。

现有限制：`config/models.json` 只有 MiniMax M3 和 DeepSeek 规则；用户可以在全局配置中追加 provider/model 精确或前缀规则。同一模型通过不同供应商或代理暴露时，需要额外规则。独立识别服务支持 OpenAI 兼容 Chat Completions 与 Anthropic Messages；不同平台仍需按其协议配置 endpoint、凭证和可选参数。

建议：增加全局 modelRules、模型别名和能力描述，显示命中的具体规则以及未匹配时的行为。将主模型的策略适配与辅助分类模型配置分开。必要时为辅助分类提供能力选项及错误诊断，避免接口不支持某参数时静默回退而用户无法理解原因。

本插件没有 RabbitMQ 队列、worker 或分阶段模型调度能力。这些属于业务运行时。策略插件适合决定在评审此类系统时应检查哪些维度，并跟随宿主实际选中的模型调整指令。

## 5. 全面审查的覆盖范围和策略预算

### 5.1 审查深度不能仅由修改风险决定

优先级：P1。

原始长请求在全新状态下得到 `review / low / quick / unclear`，domains 为空。`classifier.js:250` 默认把审查当作低风险，路由据此选择 quick；没有表达“全面程度”的独立维度。

建议区分：执行意图、工作覆盖范围、复杂度、修改影响、是否需要批准。全面只读审查可以具有较深的检查要求，同时不需要实施审批。其输出应建立检查清单并标注已查、发现问题、缺证据、未覆盖，而不是先要求实现计划。

针对用户样例，可由项目策略要求覆盖：阶段输入输出与退出条件、配置来源与更新方式、队列到 worker/模型的绑定、模型切换与请求兼容、失败恢复与幂等、向量化触发与提交一致性、检索过滤与权限、模型/索引版本、可观测性、测试与上线准备。它们是审查覆盖项，不能将所有业务名词简单添加成高风险触发词。

### 5.2 必要的授权和阶段约束可能被预算丢弃

优先级：P1。代码确认，见 `src/core/loader.js:245`、`:318`。

项目策略位于 intent 和阶段策略之前；预算不足时全部采用同一种整块丢弃逻辑，没有对必需约束保留预算。显示处虽然报告 dropped，但继续运行时可能缺少声明中的关键意图边界。最终渲染的标题和生命周期补充指令也不包含在 policy 内容字节统计中。

建议：明确不可丢弃的最小约束集，先保留用户意图和阶段边界，再分配可选背景预算；不足时显示明确配置错误或采用最小有效策略。分别展示政策正文预算和最终实际追加字节数，并检查已加载策略之间的直接冲突。

## 6. 建议实施顺序与验收

| 顺序 | 工作 | 验收要求 |
| --- | --- | --- |
| 1 | 建立隔离测试环境及真实表达回归集 | 不写真实 agent 目录；覆盖本报告全部已复现输入 |
| 2 | 修授权、否定、引用和等待阶段映射 | 未授权表达绝不进入 executing；等待阶段无“已批准”指令 |
| 3 | 增加任务关系判定、任务及计划标识 | 新审查不继承旧排障；普通对话不推进阶段；同目录会话互不串计划 |
| 4 | 完善事件记录、恢复与状态完成语义 | 能还原每次转换依据；失败或中断不等于已验证完成 |
| 5 | 统一配置 schema、覆盖语义及预览 | 错误配置不会崩溃；预览范围和网络行为明确可核对 |
| 6 | 改进审查覆盖、模型规则及交互摘要 | 全面只读任务有覆盖清单；模型切换有命中依据；显示意图和阶段 |

关键测试场景应包含完整多轮序列：排障计划 → 待确认 → 新的全面审查；待确认 → 问候；计划 → 引用/否定自主授权；批准并附带兼容约束；会话重启/分支切换；同项目并发会话；模型切换；配置损坏；小预算；执行失败或中断。

对修复效果优先统计：错误释放授权次数、新任务继承旧策略次数、不必要重复确认次数、预览与实际差异次数、状态转换记录完整率。历史数据先排除可确认的测试污染并补人工标签，才能用于衡量误判率。
